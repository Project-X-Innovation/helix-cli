# Product: Reports in HTML

## Problem Statement

Reports are currently generated, stored, and rendered as Markdown across the entire stack (agent prompts, server storage, client rendering, CLI display). Markdown limits the visual richness and dynamic layout options agents can produce. Agents are better at generating HTML than Markdown, and HTML unlocks more expressive, polished report output.

The section-level commenting and rating system (marking headings, posting comments, rating sections) must continue working identically after the format switch. All existing Markdown reports in production must remain readable.

## Product Vision

Enable agents to produce visually rich, dynamic HTML reports while preserving the full section-level feedback experience (ratings, comments, badges). This is the first step toward migrating all artifacts from Markdown to HTML.

## Users

- **Report consumers**: Team members who read, rate, and comment on generated reports in the web UI and CLI.
- **Report agents**: AI agents that generate report content during workflow execution.
- **CLI users**: Users who view report headings and section comments via `hlx library show`.

## Use Cases

1. Agent generates a new report and the user views it with rich HTML formatting (tables, styled sections, visual hierarchy).
2. User rates a specific section of an HTML report using the feedback toolbar (thumbs up/down, love).
3. User comments on a specific section of an HTML report and views threaded replies.
4. User downloads an HTML report for offline reading.
5. User exports an HTML report to PDF.
6. User views an older Markdown report that was generated before the HTML switch.
7. CLI user runs `hlx library show` to view section headings and comment annotations for an HTML report.

## Core Workflow

1. Agent receives HTML formatting instructions and generates a report as HTML with heading `id` attributes.
2. Server captures the HTML report, stores it with `.html` extension and `text/html` content type.
3. Client detects the report format (HTML vs. Markdown) and renders with the appropriate pipeline.
4. HTML headings with `id` attributes integrate with the existing anchor-based comment/rating system.
5. Users interact with section feedback toolbars and comment badges identically to the current Markdown experience.

## Essential Features (MVP)

1. **HTML report generation**: Agent prompts instruct HTML output with heading `id` attributes for anchor compatibility.
2. **HTML storage pipeline**: Server stores reports as `.html` files with `text/html` content type in both Git and blob storage.
3. **HTML rendering**: Client renders HTML reports with proper styling and sanitization (DOMPurify or equivalent).
4. **Section feedback on HTML**: Feedback toolbar, comment badges, and comment threads attach to HTML heading elements via their `id` attributes.
5. **Backward-compatible Markdown rendering**: Existing Markdown reports continue rendering via the current `react-markdown` pipeline.
6. **Format detection**: Client and CLI detect whether a report is HTML or Markdown (via file extension or content inspection) and choose the correct renderer.
7. **HTML download**: Users can download HTML reports as `.html` files.
8. **PDF export for HTML**: PDF export via `react-to-print` continues working (already DOM-based and format-agnostic).
9. **CLI HTML heading extraction**: `hlx library show` correctly parses and annotates headings from both HTML and Markdown reports.

## Features Explicitly Out of Scope (MVP)

- Converting other artifact types (non-report) from Markdown to HTML (ticket explicitly scopes to reports only).
- Migrating existing Markdown reports to HTML (existing reports remain as-is and continue rendering).
- Adding a WYSIWYG editor for manual report editing.
- Adding a format indicator field to the database schema (file extension on `LibraryItem.filePath` is sufficient for format detection).
- Removing `react-markdown` dependencies (still needed for comment content rendering in `library-comment-item.tsx`).

## Success Criteria

1. New reports are generated as HTML and render in the web UI with correct styling and visual quality.
2. Section-level feedback toolbar (rate up/down/love) works on HTML report headings identically to Markdown headings.
3. Section-level comment badges and threaded comments work on HTML report headings identically to Markdown headings.
4. Existing Markdown reports continue rendering correctly with no regressions.
5. HTML reports can be downloaded as `.html` files.
6. PDF export works for HTML reports.
7. `hlx library show` displays section headings and comment annotations for HTML reports.
8. Agent-generated HTML is sanitized before browser rendering.

## Key Design Principles

1. **Format-agnostic comment system**: The existing anchor-based comment/rating system should require zero changes. HTML headings must include `id` attributes matching the slugify convention.
2. **Backward compatibility**: Existing Markdown reports must keep working. Format detection chooses the right rendering path.
3. **Security-first HTML rendering**: Agent-generated HTML must be sanitized before rendering in the browser to prevent XSS.
4. **Minimal scope**: Only reports change format now. Other artifacts remain Markdown. Shared Markdown dependencies (e.g., `react-markdown` for comment rendering) are preserved.
5. **Same UX, richer content**: The user interaction model (rating, commenting, downloading, exporting) stays identical. Only the content format and visual richness change.

## Scope & Constraints

- **Three repos affected**: helix-global-client (rendering, format detection, export), helix-global-server (agent prompts, storage pipeline), helix-cli (heading extraction).
- **No database migration**: `LibraryItem.filePath` extension (`.md` vs `.html`) is sufficient for format detection.
- **No removal of Markdown dependencies**: `react-markdown`, `remark-gfm`, and `rehype-slug` are still needed for comment content rendering and backward-compatible Markdown report rendering.
- **Agent prompt change**: The prompts must instruct agents to include `id` attributes on all heading elements so the comment anchor system works.
- **All existing production reports are Markdown**: Runtime evidence confirms 5 recent `reportDeliverable` entries all use `.md` filenames.

## Future Considerations

- Extend HTML format to all artifact types (ticket description mentions this as a future goal).
- Remove Markdown rendering dependencies once all artifacts are migrated and comment content also switches to HTML.
- Consider a richer client-side HTML editing experience for report revisions.
- Evaluate whether agents should generate structured HTML with a consistent CSS class vocabulary for theming.

## Open Questions / Risks

| # | Question / Risk | Impact |
|---|-----------------|--------|
| 1 | How should heading `id` attributes be generated by agents to match the existing `slugify()` convention? Mismatch would break comment anchors for existing workflows. | High |
| 2 | Should HTML be sanitized with DOMPurify, or is another approach preferred? No sanitization library currently exists in client dependencies. | High (security) |
| 3 | How will the HTML renderer inject `SectionHeading` React components (feedback toolbar, comment badge) into agent-generated HTML? DOM post-processing vs. React HTML parser? | Medium |
| 4 | Will the transition cause any orphaned comments on reports that were generated as Markdown if re-generated as HTML with different heading IDs? | Medium |
| 5 | Should agent HTML prompts include a base CSS stylesheet for consistent visual quality, or should the client apply styling? | Low |
